## EdgeOne Makers 部署适配与访问速度优化

- 研究确认：EdgeOne Pages 已升级为 EdgeOne Makers，原生支持 Next.js 13.5+/14/15/16 全栈（App Router、SSR、ISR、Route Handlers、proxy.ts、图片优化）；Next.js 级 rewrites/redirects 不支持，需在 edgeone.json 配置。构建默认 `npm run build` + 输出 `.next`，构建 Node 建议 22.11.0，云函数默认 Node v20。

- `proxy.ts`：收窄 matcher 跳过静态资源，兼容 x-forwarded-host / nextUrl.host 的 Origin 校验，避免 CDN 回源头导致写操作 403。
- `next.config.mjs`：加 GitHub 图片 remotePatterns、optimizePackageImports（lucide-react/date-fns）、关闭 X-Powered-By。
- Webhook 改为最多等待 8s + after() 混合处理，避免 Serverless 冻结丢失 GitHub 事件；两个 actions 路由加 maxDuration=30。
- `lib/token.ts` 支持单行 `\\n` 转义的 GitHub App PEM（适配 EdgeOne 单行环境变量）。
- 性能：新增 0013 迁移与 schema 快照，为 config / cache_file_meta 增加 `lower(owner),lower(repo),branch` 表达式索引；多组件头像/缩略图补 loading=\"lazy\" + decoding=\"async\"。

## GitHub App 私钥超出 EdgeOne 环境变量长度限制

- 查证 EdgeOne Makers 环境变量值上限约 1000 字节，GitHub App PEM 通常 1600～3400 字节，无法直接配置。
- 新增 `lib/github-app-key.ts`：优先读单变量 `GITHUB_APP_PRIVATE_KEY`；否则按编号拼接 `GITHUB_APP_PRIVATE_KEY_1`、`_2`……（1-based、连续、最多 20 片），统一把字面 `\n` 还原为换行后交给 Octokit。
- `lib/token.ts` 改用该 helper。
- 新增 `scripts/split-private-key.mjs` 与 npm script `key:split`，把 PEM 转为单行 `\n` 后按 450 字节分片输出可直接粘贴的 env 行；已用样例 PEM 验证输出 4 片且总长正确。
- 更新 `DEPLOY_EDGEONE.md` 3.2 节、环境变量表、GitHub App 配置和排障表；更新 `README.md` 与 `.env.local.example` 说明。
- 重新验证：`npm run build`、`npm run lint` 均通过（lint 0 errors）。

### 补充：EdgeOne 环境变量值不允许空格/换行/特殊字符

- 把私钥分片方案从「字面 `\n` 文本」改为**整段 PEM 先 hex 编码再分片**：`scripts/split-private-key.mjs` 参数改为 `--max-chars`（默认 900、范围 100～950），输出值仅含 `0-9a-f`；这样不会出现空格、换行、制表符、反斜杠或 PEM 的 `-`，可直接粘贴。
- `lib/github-app-key.ts` 运行时检测 hex 分片并 `Buffer.from(..., "hex")` 解码还原 PEM，保留旧文本分片的兼容读取，最多 40 片；单变量 `GITHUB_APP_PRIVATE_KEY` 仍支持 PEM 原文或字面 `\n`。
- `DEPLOY_EDGEONE.md`：3.2 节、环境变量表、密钥生成命令统一改为 `openssl rand -hex 32`，`EMAIL_FROM` 建议纯邮箱地址（避免空格/尖括号），排障表新增特殊字符报错。README、`.env.local.example` 同步更新。
- 验证：样例 PEM 生成 4 片纯 hex，解码后与原文完全一致；`npm run build`、`npm run lint` 通过（lint 0 errors）。

## 修复部署后 GitHub 登录失败

- 用户反馈点击 GitHub 登录显示 “Could not start GitHub sign-in”。定位：better-fetch 对无 JSON body 的错误只返回 `{status, statusText}`（没有 message），旧前端只检查 `error.message` 就落到通用提示，隐藏了真实 HTTP 403。
- `proxy.ts` 的 CSRF 检查原本强制要求 `Origin`，EdgeOne 回源可能剥离该头导致空 403。改为：`/api/auth/*` 交给 Better Auth 自己校验；其他写接口依次接受 `Origin`、`Referer`、`Sec-Fetch-Site: same-origin|none`，并继续兼容 `x-forwarded-host`。
- `lib/auth.ts` 增加 `trustedOrigins: [getBaseUrl()]`。
- `components/sign-in.tsx` 改为只要有 `result.error` 就报错并显示 HTTP 状态码/排查提示，同时把错误详情打到浏览器控制台。
- `DEPLOY_EDGEONE.md` 排障表新增该错误的处理步骤。重新验证 build/lint 通过（lint 0 errors）。

## 登录报 email_not_found

- Better Auth 回调在 `userInfo.email` 为空时跳转 `?error=email_not_found`（`better-auth/dist/api/routes/callback.mjs:137-139`）。原因是 GitHub App 缺少 `Email addresses: Read only` 权限，或旧 OAuth 授权未刷新；项目自带的 setup 脚本已设置该权限（`scripts/setup-github-app.mjs:53`）。
- `lib/auth.ts` 的 GitHub `getUserInfo`：/user/emails 失败时记录 status/requestId，按 primary+verified → primary → verified → 第一条 的顺序取邮箱；仍无邮箱时用 `${id}+${login}@users.noreply.github.com` 兜底并 `emailVerified=false`，避免登录硬失败。
- `components/sign-in.tsx` 把 `email_not_found`/`user_email_not_found` 映射成可操作提示（开启 Email addresses 权限、重新安装/授权，附 GitHub App 设置链接）。
- `DEPLOY_EDGEONE.md` 第 8 步和排障表补充该权限说明。build/lint 通过（lint 0 errors）。

## 编辑页全局 404：EdgeOne 解码 %2F

- 用户用邮箱 OTP 登录后点文章编辑页出现 `The page or resource you requested could not be found.`（来自 app/not-found.tsx）。推断 EdgeOne 会把 URL 中的 `%2F` 解码后再回源，导致单段 `[path]` 路由无法匹配含目录的文件路径。
- 改为 catch-all `[...path]`：编辑页、`api/.../entries/[...path]`、`files/[...path]`、`media/[name]/[...path]`；由于 catch-all 必须是 URL 最后一段，把 `history` 移到 `entries/history/[...path]/route.ts`、`rename` 移到 `files/rename/[...path]/route.ts`，并更新 3 处前端 fetch URL。
- 新增 `lib/route-path.ts` 的 `resolvePathParam()`：把一段编码路径或多段解码路径统一还原成仓库相对路径；所有相关 route handler 的 params 类型改为 `path: string[]`。
- 验证：build/lint 通过，app-paths-manifest 确认 6 条 catch-all 路由已生成。
- 文档补充：全局 404 的重部署提示，以及邮箱账号本身无 GitHub 仓库权限、需 GitHub 登录或 collaborators 授权的说明。
